# Adding items with FFNx AddMoreItems

SolomonRing can create new item IDs 199-255 for the FFNx AddMoreItems branch.
The initial runtime implementation supports the verified 2013 English game.
Original item IDs and external references are preserved.

## Create an item

1. Import kernel.bin in SolomonRing.
2. Use Import complementary to open the matching mitem.bin and price.bin. Files
   already open in PuPuCargo/Kadowaki or Siren are shared, including unsaved edits.
3. Open Battle Items or Item Names and click **Add item...**.
4. Choose an existing item as a template, enter the new name and description, and
   choose whether the item has battle settings.
5. Edit field behavior in **PuPuCargo/Kadowaki**, battle behavior in SolomonRing's
   **Battle Items**, and prices in **Siren**.
6. Click Save in SolomonRing. It saves the kernel and both editable item files.
   Add the resulting files to your mod using its usual asset installation workflow.

New IDs are allocated at the end, starting at 199. ID 0 remains the empty item.
IDs 199-254 may have battle settings; ID 255 is field-only. Battle settings on an
existing added item can be opened from the Item Names tab. The original nonbattle
IDs 33-198 retain their original classification. New item IDs are not renumbered
or deleted by this workflow.

The current names appear in the menu/price editors, shop item choices, enemy
loot/AI data, and world-map item reward labels. Shop slots retain their numeric
IDs even when two items share a name. Existing unsaved shop and monster data is
refreshed from memory rather than reloaded from disk.

Creating a definition does not grant the item to the player or add shop stock.
Use the shop editor, monster loot editor, or an item-award script for acquisition.
FFNx enables the 24-page inventory automatically when it loads the extended kernel.

## Where behavior is defined

| File | What it controls |
| --- | --- |
| kernel.bin | Names/descriptions, and battle effect type, power, targets, statuses, flags and animation |
| mitem.bin | Field/menu effect type, target/usability flags and two effect parameters |
| price.bin | Purchase price and sale multiplier |

These records select and configure action code already present in the game.
For example, the field **Heal character** type restores `param1 * 50` HP:
copying Potion and setting param1 to 20 gives 1,000 HP of field healing. Configure
the battle record separately for its battle effect.

A new item using existing effects needs no separate DLL. A new action
or new dispatch rule needs C++ support in FFNx or a dedicated plugin interface.
AddMoreItems currently exposes no general item-to-DLL callback registration, and
entering a new numeric effect type does not implement it. Supported field types
are 0-21. Specialized systems, including Irvine's eight ammunition types, retain
their existing type counts.

## Format details

Editor section numbers are one-based. Section 8 retains 33 original 24-byte battle
records. Appended battle row 33 maps to global ID 199, through row 88 / ID 254.
Section 9 retains 166 original name/description records and extends through 223;
its row is always global ID minus 33. Names of added battle items come from
section 9, so appended battle names never overwrite the original Tent-and-later IDs.

The two item tabs edit the same canonical text for added battle items. Saving
also mirrors it into the redundant battle text. Field-only gaps before a later
battle item receive disabled battle placeholders; they stay unselectable and are
excluded from random battle selection. Field and price records remain four bytes
per global ID, extending through the highest defined item.

## Validation

The focused tests cover creation through the actual button, save/reload,
preservation of original IDs/bytes, shared unsaved edits, canonical names,
field-only gaps, ID 255 and capacity rejection, close-file guards, duplicate shop
names, and live world reward names. Synthetic kernels keep these tests usable
without original game assets.

The complete 256-ID kernel generated by the editor model was also accepted by the
FFNx native integration harness, including its paging, shop, battle and save
checks. This remains separate from an interactive in-game playthrough.
